# Nano Banana — Repair + Forward Plan

**Date:** 2026-08-21
**Status:** Tool was 100% broken. It is fixed and verified. Everything below the "Shipped" section is a decision for you.

---

## TL;DR

Google shut down Imagen 4 on **2026-08-17**. `imagen-4.0-generate-001:predict` returns 404, so every `node generate.js` call had been failing for four days. The tool is migrated to Gemini `:generateContent` and works.

The default model is now **`gemini-3.1-flash-lite-image` at $0.0336/image** — *cheaper* than the ~$0.04 Imagen 4 path it replaces. Restoring the tool costs nothing versus what it used to cost.

The bigger finding: **the JSON sidecar workflow — the tool's advertised flagship feature — has never actually worked as documented**, and the current API makes a better version of it available at the same price. That is the main decision in this document.

---

## 1. What was broken

| Problem | Detail |
|---|---|
| Dead endpoint | `generate.js:103` and `server.js:78` POST to `imagen-4.0-generate-001:predict`. Imagen 4 shut down 2026-08-17; the `:predict` surface is gone for all image models. |
| Dead parameter | `negativePrompt` was an Imagen `:predict` field. It does not exist in `generateContent`. |
| Wrong response shape | Code reads `predictions[0].bytesBase64Encoded`; Gemini returns `candidates[0].content.parts[].inlineData.data`. |

Notably, `edit_pose.js` in this same repo was *already* calling `gemini-3-pro-image:generateContent` correctly. A working reference implementation was sitting in-tree the whole time; the migration reused its call/parse pattern rather than inventing one.

---

## 2. Shipped today (no decision needed — this is done)

- **`generate.js` + `server.js` migrated** to `POST /v1beta/models/<MODEL>:generateContent`, with `generationConfig.responseModalities: ["IMAGE"]` and `imageConfig`.
- **Model selection via `--model`,** with a single flippable `DEFAULT_MODEL` constant:

  | flag | model | price |
  |---|---|---|
  | *(default)* / `lite` | `gemini-3.1-flash-lite-image` | **$0.0336** / 1K (1K only) |
  | `flash3` | `gemini-3.1-flash-image` | $0.045 / 0.5K · $0.067 / 1K · $0.101 / 2K · $0.151 / 4K |
  | `pro` | `gemini-3-pro-image` | $0.134 / 1K–2K · $0.24 / 4K |

  Exact model IDs pass through verbatim. `gemini-2.5-flash-image` is deliberately **not** aliased — it retires 2026-10-02.
- **Every run prints the model and its per-image price.**
- **Resolution gating.** `imageConfig.imageSize` is sent only to models that support it, and only when you explicitly typed `4k`/`2k`/`1080p` — never defaulted. Asking for 2K on the lite default prints a warning and renders 1K; it does **not** silently upgrade you to a pricier model.
- **Negative prompts** folded into the prompt text as `Avoid: …` so the feature survives the loss of the API parameter.
- **Error handling** now distinguishes API errors, safety refusals (surfaces `finishReason` + any text part), and unparseable responses.
- **Docs corrected** — `README.md`, `AGENTS.md`, `styles/README.md` updated; `research.md` banner-marked as superseded (not deleted).

### Verified by live test, not assumed
- Default, `--json` re-run, `--model pro`, `--model flash3`, and the Express `/generate` route all return real images (each PNG/JPEG opened and visually confirmed).
- **`imageConfig.aspectRatio` is fully authoritative.** Same prompt at 16:9 with and without `widescreen, cinematic composition` in the text produced identical **1344×768** output. Aspect words in the prompt no longer affect the canvas.
- **1K at 16:9 = 1344–1376×768**, which clears YouTube's recommended 1280×720 thumbnail size. 1K is sufficient for thumbnails on dimensions alone.
- `gemini-2.5-flash-image` silently *ignores* `imageSize` (HTTP 200, renders 1024×1024) rather than erroring.

## 3. Decisions for you

### A. Zero or negative cost impact — recommended

**A1. Repoint the JSON sidecar from "prompt" to "receipt".** ← *the main one*

The advertised workflow is: tweak one field in `image-TIMESTAMP.json`, re-run with `--json`, only that attribute changes. **It has never done that.** `buildPromptText()` reads only ~15 of the schema's fields and silently drops `subject.clothing`, `accessories`, `pose`, `scene.background_elements`, `technical.camera_model`/`aperture`/`shutter_speed`/`iso`, `composition.focus_point`, `text_rendering.*`, and `artist_reference`. A `--json` re-run doesn't give you "the same image with one change" — it gives you a materially *shorter prompt* and therefore a different image. The code's own comment admits this: *"JSON round-trip is lossy."*

Separately, four schema fields never mapped to any real Google API parameter on any surface — `meta.steps`, `meta.guidance_scale`, `meta.magic_prompt_enhancer`, `advanced.hdr_mode`. They came from the YouTube/Reddit sourcing behind `research.md`. They are decoration.

Proposal: the sidecar records what was actually *sent* — verbatim prompt string, model ID, aspect ratio, image size, seed, reference-image paths. `--json` replays that request exactly. Keeps every real benefit the feature ever had (reproducibility, versioning, provenance) and stops the tool claiming a capability it does not have. Delete the fictional fields.

*Cost: zero. Effort: medium — deletes more code than it adds.*

**A2. Replace "tweak one field" with reference-image editing.**

Google's documented way to change one thing is semantic masking on the actual pixels: *"Using the provided image, change only the [element] to [X]. Keep everything else exactly the same."* This operates on the image you already approved, so everything you didn't mention is preserved by construction rather than by hope. `edit_pose.js` is already 90% of the implementation — generalize it to `node generate.js --edit <image> "change only …"`.

An input image costs ~$0.0011 (560 tokens). An edit is one image output plus that. **Cost-neutral versus regenerating** — the better workflow is also the cheaper one.

*Cost: neutral. Effort: small.*

**A3. Fix the `cinematic` aspect-ratio collision.** `parsePrompt.js:11` treats `cinematic` as a 16:9 trigger, and the README also lists it as an aesthetic term. Typing "cinematic lighting" silently reshapes your canvas to 16:9. Since aspect words in prose no longer do anything anyway (verified above), stop parsing them out of the text and take aspect ratio from an explicit flag.

*Cost: zero — it prevents wasted regenerations. Effort: small.*

**A4. Adopt semantic negatives.** Google's current guidance is to describe the intended scene positively ("an empty, deserted street with no signs of traffic") rather than "no cars". `parsePrompt.js` currently pushes 4 baseline negatives onto essentially every generation, which now get appended as `Avoid: …` text. Worth revisiting whether they help or just consume prompt budget.

*Cost: zero. Effort: small.*

**A5. Add 429 retry with backoff.** Image models are metered in **images per minute**, and Google does not publish the per-tier ceiling. `AGENTS.md` tells agents to "run multiple in parallel with `&` + `wait`" — exactly the shape that trips an unknown limit, and today a 429 mid-batch just loses the work.

*Cost: zero. Effort: small.*

**A6. Wider aspect ratios are available than the docs admit.** The live API discovery document accepts `1:4, 4:1, 1:8, 8:1` alongside the usual set — banner shapes, absent from Google's prose docs. Relevant for channel art.

*Cost: zero. Effort: trivial.*

### B. Costs more — separate, as requested

**B1. `--batch` flag — 50% off, 24-hour turnaround.** Not a cost increase; a discount on work you'd do anyway. Lite batch = **$0.0168/image**. Six thumbnail variants overnight = $0.10. Plain API-key auth, no GCP project, no SDK — works from the existing bare `https.request`. Useless for interactive work (24h target), genuinely valuable for systematic variant generation. Does **not** compose with multi-turn refinement.

*Effort: medium — new endpoint, polling, result download.*

**B2. 2K for thumbnails carrying text — `--model flash3` at 2K = $0.101/image (+$0.067).** Google's own model card lists text as *"often blurry in 1k model."* Dimensionally 1K is already sufficient (1344×768 > 1280×720), so this buys *legibility*, not size. Suggested policy if you want it: explore on lite 1K, promote only the winner to one 2K render.

**B3. `gemini-3-pro-image` for character-consistent series — $0.134/image (4× the default).** Pro is the only model with style references (3) and the highest character-reference count (5). Lite supports **neither** character nor style refs. If a channel needs a recurring mascot or locked visual identity, lite structurally cannot do it. Buy per-series, never as a default. Note thought-text tokens bill on top at $12/M (magnitude unconfirmed).

**B4. Video-input thumbnails — `gemini-3.1-flash-image` accepts video files and YouTube URLs as context,** added 2026-05-28 and explicitly pitched by Google for *"high-quality thumbnails."* Point it at the actual video, get a thumbnail reflecting real footage. Video input token cost is unconfirmed and could be significant on long videos — sample a few seconds, don't feed the whole file. Speculative; worth one measured experiment before any commitment.

## 4. On the horizon — no action today

**Google has rewritten its image documentation around a new Interactions API** (`POST /v1beta/interactions`), not `generateContent`. On the current image-generation docs page, `generateContent` appears **zero** times. Google's position: *"While `generateContent` remains fully supported, we recommend the Interactions API for all new development… all new models, multimodal capabilities, tools, and agentic features will launch on the Interactions API."*

`generateContent` has **no announced deprecation or shutdown date**, so today's fix is not built on sand. But this tool is now off Google's documented path for images, and a second migration is likely within a year. Two things to know when that happens:
- `previous_interaction_id` gives server-side conversation state — you don't resend image bytes for multi-turn edits.
- It carries conversation history *only*, **not** `generation_config`. Aspect ratio and image size must be re-sent every turn or the model silently reverts to 1:1 / 1K. Easy way to waste an image on turn 3.

Batch has no Interactions equivalent — batch and multi-turn do not compose.

## 5. Known issues, unchanged

- **XSS in `index.html` ~line 790** — `outputArea.innerHTML = syntaxHighlight(lastJSON)`; `JSON.stringify` doesn't escape `<`/`>`. Out of scope for this work and **not touched**; nothing in the migration went near it. Still low risk in practice (localhost, self-inflicted payload), still real if this is ever hosted or shared. Fix: HTML-escape before `syntaxHighlight()`, or use `textContent` for the raw string. Worth doing if A1 lands, since that rewrites the sidecar rendering path anyway — that is the moment it becomes trivially adjacent.
- **`server.js` PORT hardcoded to 3000** — `process.env.PORT || 3000` is a one-line fix.
- **All generated images carry a SynthID watermark.** Mandatory, no opt-out, every model. No impact on YouTube use; noted so it's a known fact rather than a surprise.

---

## 6. Not verified — stated plainly

- Whether each multi-turn refinement turn incurs a full image charge. Mechanically near-certain; Google never states it. Plan on "5 turns = 5 images of spend."
- Whether `GenerationConfig.seed` produces reproducible images. The field is real; the behavior is untested.
- Per-tier images-per-minute rate limits — not published, AI Studio dashboard only.
- `9:16` and `4:3` aspect ratios were not empirically tested (only `1:1` and `16:9` were). The mapping is a straight passthrough, so risk is low.
- A genuine safety refusal was never triggered, so that error path is code-reviewed but not exercised.
- Whether PNG is honored on the Interactions surface — the discovery schema's enum lists only `IMAGE_JPEG` while the docs' samples pass `image/png`. A direct contradiction; matters for text-heavy thumbnails, since JPEG artifacts cluster around text.
- Thought-token cost magnitude on `gemini-3-pro-image`.
